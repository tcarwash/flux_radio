# First intelligible K6 GP0 microphone → Sotto RF → RTL-SDR decode

Physical session and private WAV evidence: **Nov 26, 2026** (Pacific). This is a milestone after the optimized Sotto GP0 module stopped reproducible PCM-overflow failures, but **audio quality is still poor**. The operator independently confirms they can recognize their own spoken voice in `/home/tyler/snap/firefox/common/sotto-received(5).wav` but must speak loudly and hears persistent noise/static. This subjective intelligibility report is the first positive actual end-to-end GP0-microphone voice outcome. The waveform is not a synthetic profile.

## Independently grounded receive evidence

The WAV is **17,920 samples / 2.24 seconds, signed PCM 16-bit mono at 8kHz**, SHA256 `01abae0daed8366e6749c5bac1d7ff32acdcece2d687eaf1964fa83f305f65b4`. It was matched **byte-for-byte** by independently packet-by-packet decoding the **seven CRC-valid FDV1 voice packets, eight Sotto1200 frames each**, preserved in the RTL-SDR monitor's read-only export. One BEGIN record exists; END wasn't present before the monitor was stopped. The receiver was 443.500 MHz, RTL IF -250000Hz, additional tuning -31300Hz. The user original remains unchanged.

A second copy, `/home/tyler/snap/firefox/common/sotto-received(5)-continuous-decoder.wav`, was generated from the **exact same 56 raw codec frames** using one persistent native Sotto decoder. It differs in 15,596 of 17,920 PCM samples. The old exported WAV showed near-zero startup levels for the first 16 samples **every 320ms** (repeated per eight-frame radio packet), proving codec decoder state reset produced audible packet-start dropouts. The continuous WAV removes those dropouts but doesn't lower broadband noise: 2.4–3.8kHz decoded power ~0.4 dB above 180–1400Hz power.

An optional *playback-only* speech-focused version is `/home/tyler/snap/firefox/common/sotto-received(5)-continuous-speech-focus.wav`, SHA256 `ef2fde4c1794f9aebaae022b48b2134d57737d565beb88f3f7272548e1df2215`. It applies mild stationary spectral suppression and a 150–2350Hz voice bandpass, lowering high-band energy by about **18dB relative to the voice band**. This may reduce audible static but **does not fix any on-radio capture issue**, and may remove consonant detail. All three WAVs stay on the user's workstation; don't upload raw microphone speech to a public repo.

## Evidence of voice detection versus noise

The 56 frame headers have Sotto voicing-code distribution `{0:40, 1:7, 2:8, 3:1}`; 40 frames begin with `0x13`. The physically proven *synthetic* 320+870Hz test stream has **26 of 26 frames code 1**, and decodes cleanly, with 315Hz dominant energy. The prevalence of code0 / noisy spectra in real mic capture points to insufficient periodic speech content relative to input noise (or incorrect conversion/aliasing), **not** a proven codec fault. The radio GPF1/GPT1 diagnostic from a nearby physical GP0 test showed positive module return 202 frames, no PCM loss, no missed DMA halves, no FSK/resource errors, and 28 packet preloads; that particular module return is **not independently timestamp-matched** to the precise 56-frame WAV.

The GP0 capture is a high-rate PDM-popcount source (~87k 64-bit density samples/s) with a fractional boxcar→8kHz converter and DC rejection, not a strong stopband audio decimator. A plausible source is high-frequency PDM noise aliased into the speech band. No raw GP0 PCM or PDM was preserved from this WAV, so this remains an **engineering hypothesis**. The mic-route host `sotto-api30-mic.rs.inc` already drives `REG_7D[4:0]` to code31 during capture (widest available 5-bit setting); turning that value up beyond 31 isn't possible. Digital amplification after the ADC would raise noise along with voice, so the priority is signal-to-noise ratio, filter/decimator fidelity and correct analog route, not just output volume.

## Sotto Monitor change deployed

The monitor's native decoder-state fix was committed to local `main` (`3108210`), followed by safe two-superframe lookahead flush on manual stop (`912ec8a`). **16/16 monitor tests pass.** Both changes are now loaded in the running receiver after archival of exact original audio and all eight packet events. The new process started successfully and was receiving 443.500MHz with -31300Hz click offset, RTL IF -250000Hz, `streaming_codec=true`, no errors and healthy RTL blocks. The running monitor supports continuous decoder state and recovers its last 80ms on manual stop; these changes require **no K6 MCU or module flash**.

## Next quality gate

Use the currently installed and successful `SOTTO GP0` 9,760-byte fast4+RAM-micro module (slot24) with real physical PTT and dummy load. Before trying codec modifications, compare normal speaking, silence, and a known injected **1kHz nominal 0.1V** tone at the microphone input under the new stateful receiver. Quantify 1kHz peak/noise ratio after SDR decode, speech voicing-code distribution, and GP0 diagnostic errors. A clean injected tone but noisy speech points to acoustic microphone gain/coupling/SNR; a noisy injected tone points upstream to RFIC GP0 one-bit path, PDM density/anti-alias filtering, or scaling. Do not blindly boost RFIC gain (already code31) or weaken overflow/PA watchdog guards. Preserve source PCM vs encoded RF when designing the next diagnostic.
